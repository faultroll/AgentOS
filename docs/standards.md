# 核心工程原则与开发铁律 (Standards)

本模块定义了在 Harness 内部开发时必须遵守的工程标准与“绝对红线”。

---

## 1. 必须遵循的设计原则
1. **意图与执行的隔离**：决策层（Role A）与执行层（Role B）必须剥离。
2. **基于契约的零信任输出**：
    - 优先使用 **Pydantic Schema**。
    - 严禁使用脆弱的正则表达式进行数据清洗。
3. **渐进式坚固**：每一步变更必须可运行验证，交付具体的 Markdown 验证指令。

## 2. 开发者禁止事项 (Red Lines)
- ❌ **拒绝巨大 Prompt**：严禁在单个文件中堆砌逻辑，必须模块化。
- ❌ **算力主权**：禁止为了修复特定 App 的 Bug 而向 Harness 内核注入业务硬编码。
- ❌ **越权读取**：严禁 App A 读取 App B 的 Memory 或 Prompts (App Isolation)。
- ❌ **禁止重复造轮子**：优先使用稳定的官方 MCP Server。
- ❌ **内核加固红线**：禁止在无配套单元测试的情况下修改 `kernel/`。任何 Kernel 逻辑变更必须同步更新 `tests/` 目录下的测试用例。

## 3. 计费与模型策略
- **强制白名单**：只能调用 `config.py` 列出的模型。
- **零计费红线**：所有请求必须经过 `kernel/compute/router.py` 拦截。

## 4. 物理环境限制 (Terminal Rules)
- **零执行权限**：AI 助手**不具备**代码运行、环境安装权限。
- **指令交付**：必须提供高清晰度的 Markdown 语句交由人类执行。

## 5. 认知隔离标准 (Cognitive Isolation)

我们将系统的自然语言部分视为**生产环境的二进制代码 (Artifacts)**：

- **源码文档级 (`docs/`)**：系统的“源码注释与构建手册”，记录物理实现细节（如文件路径、变量名、底层驱动逻辑）。仅供研发側维护使用。
- **生产代码级 (`prompts/`, `memory/`)**：系统的“运行态指令与认知数据”。此类文件在由模型加载执行时，即进入“运行态”。
- **运行态无感原则 (Execution Transparency)**：
    - 作为“自然语言代码”，`prompts` 和 `memory` 在运行态不应具备对物理实现层面的自感知能力。
    - **红线要求**：严禁在生产代码中引用物理路径、源码文件名或底层驱动实现。
    - **逻辑屏蔽**：正如编译后的软件不再携带源码变量名。运行态实体必须实现对物理环境的完全隔离。
